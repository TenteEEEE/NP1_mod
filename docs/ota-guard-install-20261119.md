# 自動更新抑止の初期導入・更新保証（2026-11-19）

## 検出した問題

- 所有者復旧サービスを使う新規導入経路では、OTA見張り役のunitは導入されるが、停止フラグと管理台帳を初期化していなかった。
- Web/APIバイナリ更新では、専用コピーを実行する `np1-control-ota-guard.service` を再起動していなかった。このため、更新前の見張り役が状態ファイルを生成できない場合も古いプロセスが残り、画面では自動復旧・通信遮断・監視が不明になった。
- 導入後検証は見張り役の稼働と状態ファイルの鮮度・整合性を必須にしていなかった。

## 修正

- 標準導入と所有者復旧サービス経由の新規導入の両方で、OTA管理台帳を作成し、停止フラグを有効化する。
- 所有者復旧サービス経由のアンインストールでは、通信遮断を解除してから導入前の停止フラグ状態へ戻す。
- 新規導入とWeb/API更新時に単発のguard確認を行い、状態をread-backする。
- Web/API更新時は純正サービスに触れず、NCCのOTA見張り役だけを新しいバイナリで再起動する。
- `verify.sh` で、2分以内の状態、管理中の停止方針、削除防止、Updateユーザーの通信遮断、解析済みfirmwareを確認する。利用者が明示的に更新を許可している場合は、その状態の整合性を確認する。

## 実機確認項目

- `no_ota_download` が存在し、immutableであること。
- `NCC_OTA_V1` がUpdateユーザーだけを遮断し、OUTPUTから参照されること。
- `/run/np1-control/ota-guard.json` が30秒周期で更新されること。
- Communication / DriveRec / ImageRecog / Voice / QMMFのPIDが更新前後で変わらないこと。
