# 過去2日分の経路とダッシュボードの修正

## 対象

- 11/13・11/14の走行記録を地図にも表示する。保存済みの距離・走行時間は消さない。
- ダッシュボードのグラフと経路を直近24時間にする。日付の0時で切らない。
- 現在地へ戻る操作はアイコンだけにし、表示中の地図の右下、出典の少し上へ置く。
- 中間幅では6枚のパネルをまとまりとして下寄せし、最下段の下に大きな空白を残さない。

## 調査

走行の保存集計は11/13が約16.55 km・2525秒、11/14が約57.62 km・5335秒で既に存在した。一方、地図APIは通常録画のNMEAだけを参照し、SDの通常録画が上書きされた日に座標を返せなかった。前回の作業では、この2日分の表示と他のGPS取得元の調査が不足していた。

別チェックアウトのナンバー解析で保存した実測GPSから、11/13の3320点を回収。電波の位置記録には11/14の43点が残っていた。さらにSDのイベント録画に11/13のNMEAが14本、11/14が6本存在した。通常録画だけに限定したパス・ファイル名の認識を、イベント・駐車録画のNMEAへ拡張する。raw blockの復元や純正ファイルの変更はしない。

前回は地図の取得期間だけが24時間になっており、ダッシュボードのグラフ初期値は7日だった。初期表示を `period=24h` とし、保存済み測位区間を「現在時刻−24時間〜現在時刻」に切り出す。24本の時間帯の棒を表示する。時間帯ごとの距離・時間は観測区間から按分し、全体の境界が測位区間の途中なら合計にも「約」を付ける。未測位を0で埋めない。

## 保存と表示

実測座標をNCC専用の `state/journey-tracks/YYYY-MM-DD.json.gz` へ保持する。保存は測位時刻で統合し、同じ入力を再取得しても重複しない。毎分の直近NMEA照合に加え、直近7日を5分ごとに読み取り、SDの上書きと独立させる。保存上限に達した場合は既存座標を消さずエラーとして報告する。

地図APIは保持した座標とSDの実測座標を合わせる。座標が少しだけ残る日は、それらを点として表示し、欠測を線でつながない。距離・時間の保存集計と、完全な座標列が残っているかは区別して示す。

## 導入計画・復旧

`tools/deploy.py --serial <指定serial> --action journey-update` を使用し、NCCバイナリ・電波ログ・logger状態を退避してWeb/API・brokerを更新する。AP・modem・native・plateと純正5サービスのPID・InvocationIDを前後比較する。WindowsのWi-Fiや純正サービス・設定は変更しない。

実測エクスポートの取り込みは既存の `tools/repair-radio-history.py` と `tools/device/repair-radio-history.sh` で行う。電波ログに加えて既存の座標保存フォルダーも退避し、GPS入力とSHA-256、再読取結果を残す。回収材料・生NMEA・位置・画面はignored `resources/` と `tmp/` に限定する。

## 検証

Goの区間集計・0時越え・24時間境界、座標保存・再読取・SDから消失した日の読み出し、イベント/駐車NMEA、パス逸脱拒否を検証する。ブラウザーでは24時間の初期要求・24本の棒、1000/1200px幅の下端余白、戻るアイコンと出典の位置、両日の選択を確認する。導入後は実データの両日地図、実際の24時間集計、PC/スマートフォンの操作と純正5サービスを確認する。

## 線が点だけになったとの指摘への再調査

同日、細かい経路が表示されないとの指摘を受け、APIの点数だけでなく元の測位点・接続と実画面の線を調べ直した。

- 11/13は3,335点・8区間のまま。回収元3,320点すべての座標と、同じ区間内の接続が維持されていることを実機APIと照合した。実画面でも複数の道路に沿う連続した線を確認した。
- 11/15の保管済みエクスポート6,724点のうち、実機は2,905点しか返していなかった。最初の取り込み時には座標保存機能がなく、電波照合だけに利用していたため、後から導入した座標保存へ取り込み直せていなかった。元エクスポートを既存の修復トランザクションから取り込み、6,724点・186区間を再読取。元座標の欠落・変更、元区間の接続切れはいずれも0だった。ただしこの日の座標は約20m四方の停車中の記録であり、走行経路全体の復元成功の根拠にはしない。
- **11/14の細かい走行経路は未復元。** 82点・48区間のままであり、約57.62kmの保存済み距離があることと、経路の座標列が残ることは別である。手元2チェックアウトの材料JSON/JSONL計1,031ファイル、NMEA保管先、実機のNCC修復バックアップを調査したが、同日の連続した座標列は見つからなかった。実機の当日GNSS/DriveRec/ImageRecog journalも保持されていなかった。集計アーカイブは座標を持たないので、そこから道路に沿う経路を再生成することはできない。追加復元には11/14の元NMEAまたは連続GPSログが必要。

NASバックアップの読取専用ステータスも確認したが未設定だった。別の保存先が判明するまでは、11/14の細かい経路の復元を完了扱いにしない。

再起動で `/tmp/ncc-stage` が消えた場合に取り込みが失敗することも確認し、ホスト側の `tools/repair-radio-history.py` がリポジトリー内の修復スクリプトを転送・SHA-256照合して実行するよう修正した。純正ファイルやバイナリ、Web表示の変更はしていない。GPS入力、修復スクリプト、バックアップ、適用・再読取結果は今回もignored `tmp/` に保存した。

再検証はPython全135件とGo trips/APIテストに合格。部分的なSD再読取後も復元した6,724点と線を保持する回帰テストを追加した。実機ブラウザーでは、停車中の点数だけで合格にしないよう実走行の広がりを要求し、11/13の元座標の完全一致・元区間の接続・SVGの実際の線描画を検証して合格した。撮影した地図も目視確認した。両日の距離・時間と9サービスのPID・InvocationIDは修復前と同一。HTTPSとSD動画の部分読取にも合格した。今回カメラの追加確認は2回ともストリーム取得時にHTTP 503となったため、カメラ機能の再合格とは報告していない。純正サービスの再起動や変更はしていない。
