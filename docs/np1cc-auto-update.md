# NP1 Control Center 自動更新仕様案

2026-11-22時点の設計案。所有者PCでビルド・検証した `linux/arm64` 向けの更新パッケージを GitHub Releases に登録する。導入済みのNP1は安定版を確認し、対象機種と導入状態が合うパッケージを取得・検証・適用する。初期設定は自動確認と手動適用とし、完全自動適用は設定で有効にできる。

## ビルドと配布

- 現行のビルドでは、Node.js/npmで生成した管理画面をGoバイナリ `artifacts/ncc/bin/ncc` に埋め込む。実機用ビルドではさらに、Clang/LLDで作った録画フック・注入器のSHA-256とread-back位置を `ncc` に埋め込む。所有者由来のリンク用ファイルと純正DriveRecは所有者のビルド環境に保管する。 [録画フックのビルド契約](recorder-build-contract-20261119.md)
- 本体上でも対応するGo、Node.js/npm、Python、Clang/LLD、依存ファイルと作業領域を揃えればビルドは原理上可能。現行の本体環境での一式ビルドは未検証。配布方式では一度ビルド・検証した同じバイナリを全対象機で使え、本体上でコンパイラ、依存取得、ビルド中のCPU・メモリ・ストレージを必要としない。
- 初期運用では所有者PCでタグのソースをビルドし、実機で適用・復旧を確認してから署名し、GitHub Releaseを公開する。GitHub Actionsの公開CIはテスト用に使う。配布工程を自動化する場合は、所定のビルド材料を扱える所有者管理環境で成果物を作り、署名済み成果物の公開をワークフローで行う。
- Releaseの添付物は、例えば `np1cc-update-linux-arm64.tar.gz`、`np1cc-update.json`、`np1cc-update.json.sig`。更新用パッケージには更新対象ファイルと配布に必要なライセンス情報を収める。Releaseタグ、画面の表示バージョン、バイナリが返すバージョン、マニフェストのバージョンをビルド時に照合する。
- マニフェストに形式バージョン、製品ID、対象OS/アーキテクチャ、対象の純正ファームウェア識別子、許可する更新元のビルドID、適用方式、必要な更新サービスのバージョン、添付名、サイズ、SHA-256を記録する。配布者のEd25519秘密鍵でマニフェストに署名し、NP1には初回導入時に公開鍵を固定する。強制差し替えや再公開を避け、修正版は新しいバージョンで配布する。

## 初版の適用範囲

初回に既存のADB経由の導入手順で更新サービスと公開鍵を設置する。初版は `web-worker-update` 相当の互換更新を扱い、Web/API、broker、純正OTAの監視役の再起動を伴う。brokerに依存するLEDサービスも元の稼働状態に復帰させる。本体全体の再起動は不要。純正ファームウェア、rootfs、純正サービスの操作は対象外とする。 [既存の更新・復旧手順](recovery.md)

`bin/ncc` は複数のサービスで共用され、AP・モデム・native workerなども次に起動するときに読み込む。配布できるのは、現行の録画フック・注入器との契約、各workerとbroker間の通信、既存の設定・状態データとの互換性を、署名前に更新元のビルドごとに確認したものに限る。録画フックや補助バイナリの変更、互換性を失うデータ移行、unit・ルーティングの変更を含む版は、画面で手動配備が必要と案内する。更新元や導入方式を識別できない既存機も手動配備で対応する。

## 確認とダウンロード

- NP1の専用サービスが、ネットワーク利用可能時に6時間に1回を目安に確認する。最終確認時刻を永続化し、起動時は間隔を過ぎている場合に確認する。画面からも確認できる。配布用リポジトリを固定し、公開Releaseを利用できる場合は端末のGitHubトークンを必要としない。 [GitHub Releases API](https://docs.github.com/en/rest/releases/releases?apiVersion=latest)
- 安定版 `vX.Y.Z` かつ署名済みの更新マニフェストがあるReleaseから、適用条件を満たす最大のSemVerを候補にする。モデル配布タグ、下書き、プレリリースは候補から外す。上位版が既存手順での配備を要する場合は、その旨も表示する。`ETag` が返れば条件付き取得を使い、レート制限・通信エラー時は案内された待機時間とバックオフに従う。 [GitHub REST APIのベストプラクティス](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- 自動確認で取得するのはRelease情報と署名済みのメタデータまで。パッケージのダウンロードは手動適用時、または完全自動設定時に開始する。既定ではNP1のWi-Fi上流を使い、4Gは明示的に許可したときだけパッケージ取得に使う。Wi-Fi失効時に4Gへフォールバックしないことを通信経路で保証できるまで、その条件での自動取得を有効にしない。
- Releaseの添付ファイルを HTTPS で取得し、正規の配布先とリダイレクト先を検証する。最大サイズと空き容量を確認して専用の一時名へ書き込み、署名が保証するサイズ・SHA-256の一致後に完成扱いとする。外向きの通信は通常のTLS証明書検証を行う。 [GitHub Release添付のAPI](https://docs.github.com/en/rest/releases/assets)

## 適用と復旧

1. Webとは独立した更新サービスが処理する。ダウンロード側は非特権で動かし、適用側は固定された更新操作と設置済みのスクリプトだけを実行する。root側は専用領域へ取り込んだ実体を再検証する。展開時は許可した通常ファイルと上限サイズだけを受け入れる。WebからはURL・パス・コマンドを渡せない設計とし、操作APIには既存の同一Origin・CSRF検証を使う。 [既存のAPI契約](api-openapi.yaml)
2. 更新と既存の配備・復旧の間で排他を取り、署名、互換性、空き容量、候補バイナリのself-testを確認する。完全自動適用は、車両が停車中で電源を維持できると確認でき、競合する操作がない場合に限る。その状態を信頼できる形で取得するまでは、利用者が停車・電源維持を確認して手動適用する。
3. 現行バイナリの復旧コピーと更新状態を `/overlay/owner-apps/np1-control/` 配下へ永続化してから、同じファイルシステム内で原子的に切り替える。設定、録画、資格情報はそのまま使う。候補の配置・復旧コピー・未確定の記録を同期してから切り替え、起動時には関連サービスがバイナリを読み込む前に未確定の更新を復旧する。
4. Web/APIとbrokerなど影響するNP1CCサービスだけを再起動する。稼働中バイナリのバージョンまたはハッシュ、HTTP 80とHTTPS 443のUI/API応答、broker経由の読み取り、録画フックのread-back、純正OTA監視の正常性を確認する。Communication、DriveRec、ImageRecog、Voice、QMMFについて更新前後の稼働状態と、取得可能な機能指標を確認する。検証がすべて通った時点で成功を確定する。適用中はUI・ライブ表示が一時切断する。
5. 適用後の確認失敗、起動失敗、確定前の電源断では直前の動作確認済み版へ戻し、同じ項目で復旧を確認する。更新サービスが異常終了した場合も、systemdから復旧処理を起動する。復旧に失敗した場合はADBで確認できるよう記録する。失敗した同じパッケージは自動適用を繰り返さない。直前の動作確認済みコピーへの明示的なロールバックを用意し、ネット経由では過去に確定した最高バージョンより古い版を適用しない。

## 管理画面

「システム › 設定・バックアップ」に「NP1 Control Center の更新」を追加する。現在版、候補版、変更内容、ダウンロード容量、最終確認、進捗、最後の結果を表示する。操作は「更新を確認」「ダウンロードして適用」「直前の版に戻す」。自動確認のオン／オフ、完全自動適用、4Gダウンロード許可を端末設定として保存する。現行の純正ファームウェア更新制御は同じ画面の「本体の自動更新」から確認できる。 [現行の管理画面](usage.md)

## 受け入れ試験

- Release署名、バイナリのバージョン一致、対象外タグ・機種・ビルドの除外、改変・破損・容量不足時に適用を開始しないことを確認する。
- 通信切断、Wi-Fiから4Gへの切替、同時要求、適用中のプロセス異常終了、同期・切り替え・検証の各段階での電源断を再現し、現在版または正常な旧版で起動することを確認する。
- 実機で手動適用、完全自動適用の待機条件、Webの再接続、設定・録画の保持、旧版への復帰を確認する。関連workerが更新後に再起動した場合も検証し、純正Communication、DriveRec、ImageRecog、Voice、QMMFの機能確認とカメラ検証・Web E2Eを実施する。
