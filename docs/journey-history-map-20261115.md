# 走行履歴・地図・電波位置の修正（2026-11-15）

## 要求と変更

- ダッシュボードの地図は、JSTの当日だけでなく「現在時刻−24時間〜現在時刻」のGPS経路を取得する。概要・詳細で共通化し、0時をまたぐ連続区間を分断しない。
- 地図をPCのドラッグ・スマートフォンの1本指操作で移動できる。移動中は測位更新やリサイズで元に戻さず、「現在地に戻る」で追従を再開する。カメラ小窓とボタンが重ならない配置とする。
- 履歴画面の順序を「走行の記録 → 走行履歴マップ → 日別の詳細」に変更。地図と詳細の日付を連動させる。
- GPS経路と電波観測を独立させる。電波ヒートマップは初期オフで、任意にオン・オフできる。電波の絞り込みや取得失敗でGPS経路を消さない。
- 電波観測の位置紐づけを、リアルタイム位置と録画確定後の再照合の両方で行う。

## 原因と読み取りで確認した状態

旧履歴地図は電波観測の位置付きデータだけを使用しており、録画側のGPS経路を読んでいなかった。さらに電波記録は5秒以内のNMEA測位を要求していたが、NMEAは録画クリップ確定時に約3分遅れて公開される。このためGPSが動作していても、電波観測の取得時に紐づけできない条件があった。

読み取り専用で確認した時点では、電波観測15,016件、位置なし14,896件、位置付き120件。一方、録画側には有効なGPS測位6,724点・186区間が存在し、現在のGPSも取得できた。純正Communication / DriveRec / ImageRecog / Voice / QMMFはactive。観測時点の生データ・アクセス先・位置はignored `tmp/` 内だけに保存している。

ローカル検証完了後の再確認では管理APIへ到達できなかったため、純正5サービスの最終状態は再確認できていない。上記activeは初回の読み取り時点の結果。サービス操作・ネットワーク設定変更による復旧は行っていない。

旧ダッシュボードには既に2日分を取得する処理があったため、「当日分しか要求していなかった」とは断定しない。修正では24時間の時刻範囲をAPIに明示し、日別APIによる区間番号の再採番を避ける。前日分、JSTの0時前後、24時間の両端、古すぎる点・未来の点をテストする。

## 実装とデータ保全

`GET /recordings/track` は従来の日付指定に加え、最大24時間の `from` / `to`（RFC3339）を受け付ける。両端の実測点を含み、無効測位・5秒超の欠測・異常な飛びをつながない。日別指定は従来どおりJSTの0時以上、翌0時未満。

`GET /radio/history?date=YYYY-MM-DD` でGPS地図と同じJST日の電波を取得する。従来の `days` 指定も維持し、日付との同時指定は拒否する。

電波の位置は次の順で補う。

1. 電波観測時刻に対応する新しいNMEA測位があれば使用する。
2. なければ、既存のGPS判定で有効と確認できた毎秒の純正位置を使用する。古い精度値を流用せず、精度不明として扱う。
3. 1分ごとに直近15分の確定済みNMEAを読み、観測時刻との差が5秒以内の最も近い測位を保存済み電波に紐づける。補間や離れた時刻の座標の流用はしない。

補完対象は位置なし・無効な位置、または精度確定前の毎秒位置。既存の有効なNMEAとの紐づけ、電波値、観測時刻、未知のJSONフィールドは維持する。ログ本体と直前のローテーションの両方を対象にし、変更のあるファイルだけを一時ファイル経由で置換してSHA-256でread-backする。

位置の追記で既存ファイルが大きくなっても記録を捨てない。新規追記のローテーションは16 MiB、修復済みファイルの読み取り上限は64 MiB。修復は変更行だけをメモリに保持し、表示側も直近20,000件へ絞る途中のメモリを制限する。

## 実機導入・過去データ修復

初回は読み取り専用の指示に従って導入を保留した。その後、下記の明示指示に基づいて実機導入・修復・検証を実施した。

### 追加指示に基づく導入内容（2026-11-15）

利用者から最新mainへのリベースと実機導入・検証を指示されたため、上記の読み取り専用制約はこの導入作業について解除された。`origin/main` の `93cbfdb` に競合なくリベースした。WindowsのWi-Fi操作、純正サービスの変更は行わない。

`tools/deploy.py --serial <指定serial> --action journey-update` から `tools/device/journey-update.sh` を呼ぶ。導入直前にNCCのWebを止め、既存バイナリ・電波ログ2世代・logger状態を所有者情報ごと `recovery/journey-*` に保存し、SHA-256を記録する。Web/API・brokerだけを既存の更新処理で入れ替え、設置先と稼働バイナリをread-backした後、過去の紐づけ修復を行う。失敗した場合は元のバイナリと電波ログ・logger状態へ復旧する。AP・modem・native・plate各ワーカーと純正5サービスのPID・InvocationID・稼働状態を前後比較する。

実機の事前確認では対象11サービスがactive、`/overlay` の空きは約709 MiB、`/tmp` は約1,083 MiB。実機のPythonは標準 `json` がない最小構成、`/overlay` は `noexec` のため、設定ディレクトリの取得とread-back判定はNCC自身で行い、修復は `/run/np1-control/ncc` を使用する。マウント設定やPython環境は変更しない。

### 導入結果

- `93cbfdb` を取り込んだバイナリを実機へ導入した。設置先・broker実行用・Webプロセスの3つのSHA-256がローカル成果物と一致した。
- 当初のPython依存・noexecに対応して再試行した。noexecで修復が起動できなかった回は、更新スクリプトによるバイナリ・電波ログの自動復旧とNCCの再稼働を実機で確認した。
- SDに残っていたGPSで328件を補完した。さらに初回読み取りで保存していたGPS実測6724点を使い119件を補完。追加447件すべての座標・測位時刻が保存済み実測点と一致し、電波観測との時刻差が5秒以内であることを確認した。
- 位置付き記録は120件から567件へ増加。修復前の15,158件の電波値・観測時刻・未知フィールド、既存のGPS付き120件はすべて保持された。現在利用可能な実測GPSに5秒以内で対応する未処理記録は0件。
- 残る約1.46万件には、利用可能なSDのGPS・保存済み実測エクスポートに対応する測位がない。座標を推定して埋めず、位置なしの原記録として保持している。
- AP・modem・native・plateワーカー、純正Communication / DriveRec / ImageRecog / Voice / QMMFの計9サービスは、導入前と画面検証後でPID・InvocationID・active状態が一致した。
- HTTP 80 / HTTPS 443のパスワードなしセッション、実際の前方・車内JPEG、MP4 Range、バックアップの秘匿情報除去を確認。WindowsのWi-Fi操作はしていない。

実機の電波データは全点でメートル精度が未記録だったため、初期のエリア集計だけでは電波が表示されない問題も修正した。精度不明の測定点は初期オンとし、色付き・破線の点として重ねる。精度不明点をエリア集計に混ぜたり、HDOPをメートル値へ置き換えたりはしない。GPSの青い経路は引き続き独立して表示する。

材料はignored `resources/journey-repair-20261115/`、実機ログ・スクリーンショット・検証結果はignored `tmp/` に保存した。実機にも `recovery/journey-*` と `private/radio-repair-*` のバックアップ・計画・read-backを残している。経路や接続先を公開ドキュメントへ転記しない。

再現用スクリプト: `tools/device/repair-radio-history.sh`。更新済みのNCCバイナリが必要。

- `plan`: 読み取り専用。残っているNMEAから照合し、対象件数・既に位置付きの件数・照合可能・照合不能・使用した測位点数・GPS読み取り範囲の省略有無（`sourceTruncated`）を出力する。
- `apply [TRACK_FILE]`: NCCのWebサービスだけを停止し、元の電波ログ2世代を所有者情報とSHA-256付きで `private/radio-repair-*` へバックアップ。紐づけを適用し、所有者を復元、再読取で追加の照合候補が0件になることを確認して元の稼働状態へ戻す。適用・read-back失敗時は元のログへ復旧する。任意のTRACK_FILEは以前の実測GPSエクスポートで、コピーとSHA-256をバックアップへ保存して同じ材料で再読取する。
- `restore BACKUP_DIRECTORY`: バックアップのSHA-256を検証して2世代を復元し、復元後のハッシュも確認する。

純正サービス、rootfs、raw block、WindowsのWi-Fi設定には触れない。ADBで呼び出す場合はserialをCLI引数に渡し、機器情報や実行ログはignored領域に保存する。適用後は、APIの位置付き件数、該当日のGPS地図と電波の重なり、再実行の冪等性、純正5サービスを確認する。

以前の実測エクスポートを使うホスト側の手順は `python tools/repair-radio-history.py --serial <指定serial> --measured-track <private export>`。転送のSHA-256をread-backし、実機変更は上記の再現可能なdeviceスクリプトに任せる。GPSのエクスポートは取得元が `stock-recording-nmea` であること、日付・座標・未来時刻を検証し、推定位置の入力を拒否する。

GPSファイルも実測エクスポートも残っていない時間や測位できなかった時間は復元できない。距離・時間だけを保存した走行集計から座標は生成しない。GPS読み取りには既存のインデックス上限があるため、`plan` の照合不能件数と `sourceTruncated` を確認する。今回の修復は `sourceTruncated:false`。
