# 高度化PICSの実験機能

NP1 Control Centerで「システム → 高度化PICS」を開きます。ダッシュボードのライブ映像直下にある「信号」からも開けます。「受信記録」が最初に表示され、「受信・発話設定」で表示、VOICEVOX、進行方向の絞り込みを設定できます。初期状態では受信と表示がオン、VOICEVOXと進行方向の絞り込みはオフです。

「信号の状態を本体LEDに表示する」をオンにすると、赤は左、青点滅は中央、青は右に出ます。複数の灯色は同時に表示し、進行方向の絞り込みをオンにしている場合は対応する灯器を使います。新しい受信が途切れると信号のLED表示が終了します。ナンバーの点灯通知や画面連動が動作中はそちらが優先されます。初期状態ではこの設定はオフです。

表示・発話は高度化PICSの補助情報です。現地の信号を確認してください。灯色は最終受信から最大1.75秒、発話とLED表示は1.25秒の鮮度を使います。Webは受信からの残り有効時間を本体から受け取り、通信中も期限を過ぎた表示を自動的に消します。既に受信した信号の情報が更新されない場合は「信号の更新停止」と表示します。

## 発話と音声キャッシュ

- 残り時間の目安が得られると「青まであとおよそ27秒です」のように案内し、約10秒前と5、4、3、2、1秒を読み上げます。
- 残り時間が不明でも、同じ交差点で赤が続く灯器群と同じ変化をした別の灯器群を確認できれば案内します。他方の青点滅で「別方向の信号が青点滅しています」、他方が赤に変わったら「まもなく青になる見込みです」と案内します。対象灯器の赤→青が受信できた時点で「信号が青になりました」と発話します。
- 共通のVOICEVOX設定で、対象の声の定型文と1〜99秒を組み立てるための45クリップを本体に保存します。設定で音量と試聴を確認できます。声を変えると不足分を準備します。

Type 2の残り値は1〜8の段階です。同じ交差点・灯器・段階で青までの観測値5件がそろい、その差が2秒以内の場合に、中央値から秒数の目安を表示します。 [参照実装の表示仕様](https://github.com/yumu19/ble-pics-viewer/blob/d97a27872ef1251a743fe8c1d5eadf0058e553a6/web/README.md#表示内容)

## 受信記録・地図・周期

「受信記録」で日本時間の日付と交差点を選びます。PCでは地図と時刻順のカードを横に並べ、スマートフォンでは縦に配置します。カードを選ぶと対応する位置を地図の中央に表示し、目印を選ぶと対応する記録を一覧で示します。青い点がNP1の受信地点、橙の点がType 1で得られた交差点位置です。「灯器ごとの観測周期と予測」は一覧の下にあります。

灯色や段階が変わったときと、同じ状態が続く場合は15秒ごとに記録します。位置が取れなくても灯器番号・灯色・段階・受信時の残秒の目安を記録します。録画のNMEAから走行履歴が保存されると、時刻差3秒以内の実測点を履歴表示時に補完します。元の受信ファイルにも反映する場合は、`tools/device/pics-history-backfill.py` で日付を指定できます。既定は復旧件数の確認のみです。`--apply` は本体の元ファイルをバックアップし、対象日の座標と方位を保存して照合します。

信号LEDは、信号状態が有効な間は赤を左、青点滅を中央、青を右に出します。複数の灯器で灯色が異なる場合は同時に点きます。受信待ちや更新停止の間は本体の通常LED設定を使うため、通常設定が虹色の場合は虹色に戻ります。

同じ灯器で一回の赤→青から次の赤→青まで、受信が継続した区間だけを一周として測ります。灯色ごとの実測中央値と回数を表示します。直近5回が2秒以内にそろうと予測周期も表示します。保存の上限は一日約2 MiB、全体約48 MiBです。

進行方向は受信直前の最大3分のGPSから求めます。3点で16 m以上移動し、途中の向きがそろう測位を使います。停車している場合は停車直前の移動区間を使います。絞り込みをオンにする場合は「受信記録」で交差点を選び、下の「この交差点の横断方向を登録」から、現地で確認した灯器ごとの横断方向を真北0°の方位で入力します。横断方向と進行方向を約25°以内で照合します。方向が未確定の灯器は受信履歴で確認できます。 [警察庁 高度化PICS運用ガイドライン](https://www.npa.go.jp/laws/notification/koutuu/kisei/kisei20260310.pdf#page=5)

## 純正Bluetoothと自動再接続

NP1の純正 `NEventWatcherCom` が提供する `NPBTLEHandler` に、本体ブローカーが受動探索を要求します。広告と終了は純正バスの `Evt048` で受け取り、送信元のプロセスと要求元PIDを照合します。純正サービスがメーカー固有データを追加広告データ（ADタイプ `0xff`）に入れる場合も受信できます。

固定アドレスの送信機からは、純正Bluetoothが探索1回につき1件だけ広告を通知することを実機で確認しました。通常は1秒探索し、終了通知から40 ms後に次を要求します。周囲の広告が1件も通知されない探索の次は5秒探索し、広告が届いた回の終了後に1秒探索へ戻します。拒否が明示された場合は次をすぐ試せるようにし、前の探索の成立が不明な場合はタイマーが満了するまで待ちます。

探索の拒否、接続切断、13秒間の通知途絶を検知すると、受信状態と進行中の発話をいったん取り消します。純正サービスへの要求は250 msから最大4秒まで待ち時間を広げて再試行します。受信時刻をブローカーからWebに引き継ぎ、最終受信から1.65秒で残り秒数と発話・LEDの判定を、1.85秒でWebの灯色を失効させます。ブラウザーは通信中でも独自に期限を進めます。受信が戻ったら新着の灯色から案内を再開します。同一送信元で完成済みの学習値は保持し、受信が途切れた区間は灯色変化や周期に使いません。同じ交差点ID・灯色・段階を持つ別送信元の広告は表示の鮮度を更新できます。送信元をまたぐ青の遷移には発話を出しません。設定をオフにすると要求を止めます。

試験機の再起動時は、純正Bluetoothが既存の相手にClassic Bluetoothで再接続を試みる間、探索開始に成功してもコントローラーから広告が上がらない区間がありました。純正HCIの記録で `HCI_Create_Connection`、`Page Timeout`、BLE広告通知を照合しました。 [Bluetooth SIG Core Specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host-controller-interface/host-controller-interface-functional-specification.html)

`tools/pics-ble-observe.py` は、USBで接続したNP1の既存の探索を観測します。`--serial` で機器を指定し、`--seconds` と `--output` で期間と保存先を設定します。JSONLは `tmp/` または `docs_private/` に保存し、探索の開始時刻・要求秒数・終了時刻、対象広告の匿名送信元・RSSI・復号の可否を比較できます。試験用広告を送る場合は、162PCの `tools/remote/pics-test-advertiser.py --stable-address` と観測側の `--bench-tag` に同じタグを指定します。受信に使うのは本体の純正BLEです。

対象ファームウェアでは `NEventWatcherCom` のリアルタイムCPU枠が初期状態で0のため、ファームウェア読み込み後にBluetoothの優先度99のスレッドを開始できませんでした。既存のpost-bootスクリプトの冒頭から所有者用の補助スクリプトを起動します。純正サービスのCPUグループが準備でき次第、Bluetoothの初期化に間に合うように1秒当たり20 msの枠を設定します。既存設置への追加は `tools/device/pics-stock-rt-install.sh plan` と `apply` で行い、次回起動から適用します。復旧は同スクリプトの `rollback` で所有者用ブロックと補助スクリプトを戻した後、NP1を再起動します。

## 実機で確認した範囲

再起動後、ファームウェアの読み込みより先にCPU枠が設定され、稼働中のブローカーは探索の開始・終了と広告を受け取りました。安定後に162PCから固定アドレスで約10分間送った試験広告を純正BLEで520件受信し、赤→青60回をすべて検出しました。受信間隔は中央値1.142秒、95パーセンタイル1.342秒、最大1.570秒でした。試験は予約メーカーIDを使いました。

最終版の再起動試験では広告受信を再開しましたが、純正Bluetoothの接続再試行中に最大21.733秒の受信間隔が残りました。状態が途絶した区間では表示と発話を失効させます。

VOICEVOXの45クリップが本体に揃っていることと、赤→青の受信から「信号が青になりました」のキャッシュ済み音声を取り出せることを、スピーカーを使わずPCMで確認しました。別方向の青点滅、まもなく青、27秒、10秒、5〜1秒もキャッシュからPCMを確認しました。実交差点での受信範囲と周期の推定精度は公道での観測が必要です。

LEDの実機試験では、模擬信号で左右の点灯と中央の点滅を指示し、条件不一致のナンバーの白点灯後に信号表示へ復帰し、設定をオフにすると終了することを確認しました。模擬入力を止めてから1.689秒で信号表示の指示が解除されました。計測はLEDドライバーの指示状態を読み取りました。

実機には `tools/device/web-worker-update.sh` で所有者用Webとブローカーを更新しました。バックアップの旧版バイナリーを復旧に利用できます。更新中は純正6サービスの呼び出しIDを照合し、再起動後は前方・車内のJPEGおよびSD録画のMP4範囲読み取りを確認しました。探索の正常終了、通知途絶時の再接続、古い信号の無効化は自動テストで検証します。

専用画面への変更後、幅1440 pxと390 pxの実機ブラウザーで、システムの専用タブ、設定画面、ダッシュボードのリンク、履歴の取得を確認しました。地図と記録の相互選択、日付・交差点の絞り込み、周期表示は合成記録を使って検証しました。所有者用更新の前後で純正6サービスの同一性と、更新後の前方・車内JPEGおよびSD録画の読み取りを確認しました。
